# راه‌اندازی مدیریت و پیام‌های مشترک

## دو حالت اجرا

در پیش‌نمایش Vite، برنامه به‌صورت محلی کار می‌کند. رمز اولیهٔ پنل `admin` است. کاربران، موبایل‌ها و پیام‌ها فقط در همان مرورگر هستند. این قفل سمت مرورگر، مرز امنیتی واقعی نیست و نباید برای انتشار عمومی اطلاعات خصوصی به آن اتکا کرد.

سرور همراه پروژه در `server/index.mjs` برای ذخیرهٔ مشترک، کنترل مجوزها و دریافت پیام سایر دستگاه‌ها آماده شده است. این سرور باید جداگانه روی هاست Node.js اجرا شود. اجرای سرور در محیط پیش‌نمایش انجام نشده است.

## اجرای سرور

به Node.js نسخهٔ 22 یا بالاتر و یک دیسک دائمی نیاز است.

1. وابستگی‌های پروژه را با `npm install` نصب کنید.
2. خروجی فرانت‌اند را با `npm run build` بسازید.
3. برای اولین اجرا `ADMIN_PASSWORD` را تنظیم کنید. اگر تنظیم نشود، رمز اولیه طبق درخواست `admin` است. قبل از انتشار آن را تغییر دهید.
4. دستور `node --import tsx server/index.mjs` را اجرا کنید.
5. در اجرای محلی، سایت در `http://127.0.0.1:3001` در دسترس است. همان سرور، خروجی `dist` و API را ارائه می‌کند. برنامه به‌صورت خودکار اتصال را تشخیص می‌دهد.

## تنظیمات محیط

| متغیر | کاربرد |
| --- | --- |
| `PORT` | پورت داخلی؛ پیش‌فرض `3001` |
| `HOST` | نشانی گوش‌دادن؛ پیش‌فرض `127.0.0.1`؛ در کانتینر معمولاً `0.0.0.0` |
| `ADMIN_PASSWORD` | فقط رمز اولین راه‌اندازی؛ پس از آن از پنل تغییر دهید |
| `DATA_DIR` | مسیر دیسک دائمی داده‌ها؛ پیش‌فرض `server-data` |
| `PUBLIC_ORIGIN` | آدرس دقیق سایت، مانند `https://example.com`؛ بدون اسلش پایانی |
| `NODE_ENV` | برای انتشار `production` |
| `COOKIE_SECURE` | برای HTTPS مقدار `true` |
| `TRUST_PROXY` | فقط اگر یک پراکسی مورداعتماد پیش روی سرور است، `1` |

پراکسی معکوس HTTPS باید هر دو مسیر `/api/*` و سایت را به همین سرویس هدایت کند. برای اجرای محلی HTTP، `NODE_ENV=production` یا `COOKIE_SECURE=true` نگذارید؛ مرورگر کوکی امن را روی HTTP نمی‌فرستد. این پروژه روی هاست صرفاً استاتیک، امکانات مشترک سرور را نخواهد داشت.

## دسترسی‌ها

- مدیر با رمز وارد می‌شود. نشست ۳۰ دقیقه‌ای در کوکی HttpOnly و SameSite=Strict قرار دارد؛ در انتشار، Secure نیز فعال است.
- درخواست‌های نوشتن نیازمند هدر اختصاصی و مبدأ مجاز هستند. مسیرهای مدیریت در خود API مجوز مدیر را بررسی می‌کنند.
- رمز مدیریت با scrypt و نمک تصادفی هش می‌شود. تلاش‌های ورود محدود می‌شوند.
- کاربران کلید تصادفی اختصاصی دارند؛ هیچ فهرست عمومی از کاربران و موبایل‌هایشان منتشر نمی‌شود.
- «کد بازیابی» داخل حساب شخصی، کلید ورود به حساب در دستگاه دیگر است. آن را عمومی نکنید. این نسخه ورود پیامکی و بازیابی از طریق SMS ندارد.
- موبایل اختیاری است، اعتبار قالب آن بررسی می‌شود اما مالکیت شماره تأیید پیامکی نمی‌شود. برای کودکان، شمارهٔ والد یا سرپرست درخواست می‌شود.
- پیوست‌های پیام فقط برای صاحب پیام یا مدیر قابل دریافت هستند. SVG، HTML و فایل اجرایی پذیرفته نمی‌شوند. نوع فایل، امضای اولیه و سقف حجم بررسی می‌شوند؛ اسکن بدافزار جداگانه برای استقرار پرترافیک توصیه می‌شود.
- رسانه‌های بارگذاری‌شده توسط مدیر عمومی هستند و برای نمایش در بازی استفاده می‌شوند.

## داده و پشتیبان

`server-data/store.json` شامل کاربران، کلیدهای هش‌شده، محتوا، پیام‌ها و تنظیمات است. `server-data/files` فایل‌های واقعی را نگهداری می‌کند. این پوشه را در Git، پوشهٔ public یا فضای عمومی وب قرار ندهید. سرور با دسترسی محدود فایل می‌نویسد.

از کل پوشهٔ داده‌ها در فضای خصوصی و ترجیحاً رمزگذاری‌شده پشتیبان بگیرید. برای نسخهٔ سازگار، سرویس را هنگام گرفتن snapshot متوقف کنید یا از snapshot اتمی دیسک استفاده کنید. پشتیبان JSON داخل پنل فقط محتوا و تنظیمات را شامل می‌شود؛ کاربران، رمزها و بایت‌های رسانه‌ها در آن نیستند.

ویرایش‌های حالت محلی خودکار به سرور منتقل نمی‌شوند. می‌توانید از بخش پشتیبان، محتوای محلی را خروجی بگیرید و در پنل متصل وارد کنید. رسانه‌های محلی باید دوباره روی سرور بارگذاری شوند. پیام‌های محلی در سرور وارد نمی‌شوند.

این سرور برای یک فرایند و یک دیسک دائمی طراحی شده است. برای چند نمونهٔ هم‌زمان یا ترافیک بالا، ذخیره‌سازی فایل JSON و نشست‌های حافظه‌ای باید به دیتابیس و مخزن نشست مشترک مهاجرت کنند. با راه‌اندازی مجدد سرور، مدیر باید دوباره وارد شود.

## به‌روزرسانی سروری که بالا آمده است

فایل‌های جدید را روی همان پوشهٔ پروژه در سرور (مثلاً `/root/gamnasr-deploy`) بریزید و جایگزین کنید. پوشهٔ داده‌ها (`server-data` یا `gamnasr-data`) و `node_modules` را دست نزنید. سپس روی سرور فقط یک دستور بزنید:

```
cd /root/gamnasr-deploy && sed -i 's/\r$//' update.sh && bash update.sh
```

اسکریپت `update.sh` این کارها را خودکار انجام می‌دهد: پیدا کردن سرویس systemd مربوط به همین پوشه، پشتیبان‌گیری از `store.json` در پوشهٔ `backups`، نصب بسته‌ها، ساخت خروجی فقط اگر لازم باشد، ری‌استارت سرویس و بررسی سلامت API. اگر سرویسی پیدا نکند، دستورهای جایگزین را چاپ می‌کند.

ری‌استارت پس از هر به‌روزرسانی الزامی است: سرور هنگام شروع، hash اسکریپت داخل `dist/index.html` را برای هدر CSP محاسبه می‌کند؛ اگر فایل جدید بدون ری‌استارت جایگزین شود، صفحه سفید می‌ماند. با ری‌استارت، نشست مدیر بسته می‌شود و باید دوباره وارد شوید.

روش دستی همان سه گام است: `npm install`، سپس `npm run build`، سپس ری‌استارت سرویس Node.js.

محتوای ذخیره‌شدهٔ قبلی حذف نمی‌شود. فیلدهای تازه مانند عنوان و نماد «رقابت» هنگام خواندن با مقدار پیش‌فرض کامل می‌شوند، بنابراین سایت فعلی شما بدون خطا بالا می‌آید.

## بخش رقابت

جدول رقابت از روی پیشرفت ثبت‌شدهٔ هر حساب ساخته می‌شود:

| بخش | امتیاز هر واحد |
| --- | --- |
| درس کامل‌شده | ۱۰۰ |
| هر ستاره | ۲۰ |
| رهرو همراهی‌شده | ۳۰ |
| هر مدرک | ۲۰۰ |
| بهترین مومنتوم | ۵ |
| نعمت شکرشده | ۲ |
| روز کامل برنامهٔ روزانه | ۱۰ |

نکته‌های مهم:

- روی سرور، هر کاربر باید خودش «شرکت در رقابت» را روشن کند و یک نام نمایشی بگذارد. تا وقتی روشن نکند، نامش در جدول دیگران دیده نمی‌شود. شماره موبایل و پیام‌ها هرگز در جدول نمایش داده نمی‌شوند.
- در حالت محلی، جدول فقط حساب‌های همان مرورگر را مقایسه می‌کند و چیزی به بیرون فرستاده نمی‌شود.
- امتیاز از روی پیشرفتی محاسبه می‌شود که مرورگر کاربر ارسال کرده است. مانند هر بازی مرورگری، کاربر آگاه می‌تواند این داده را دستکاری کند؛ بنابراین جدول برای انگیزه مناسب است، نه برای داوری رسمی یا جایزهٔ حساس.
- مدیر می‌تواند این بخش را از «ظاهر و تنظیمات سایت / بازی و دسترسی» خاموش کند؛ در این حالت تب رقابت از منو برداشته می‌شود و مسیر API آن هم پاسخ نمی‌دهد.

## بررسی استقرار

آزمون‌های API در `server/security.test.mjs` قرار دارند. با `node --import tsx --test server/security.test.mjs` اجرا می‌شوند. این آزمون‌ها در محیط ساخت فعلی اجرا نشده‌اند.

پس از استقرار، ورود نادرست، خروج مدیر، انقضای نشست، ارسال پیام از مرورگر دوم، پاسخ مدیر، ثبت موبایل، دانلود پیوست مجاز و رد دانلود توسط کاربر دیگر را بررسی کنید. پخش صدا و مجوز میکروفون نیز روی موبایل واقعی آزمایش شوند.

برای بخش‌های تازه: روشن‌شدن چراغ تأیید با پاسخ درست، روشن‌نشدن آن پیش از پاسخ، و در بخش رقابت، روشن‌کردن شرکت از یک مرورگر و دیده‌شدن نام نمایشی در مرورگر دوم را آزمایش کنید. پس از خاموش‌کردن شرکت، نام باید از جدول حذف شود.

توجه: سایت شما در حال حاضر روی `https://86.107.47.228/` با گواهی خودامضا بالا آمده است. مرورگرها برای این آدرس پیام هشدار امنیتی نشان می‌دهند. اگر یک دامنه به این سرور وصل کنید و گواهی معتبر بگیرید، هشدار برداشته می‌شود و `PUBLIC_ORIGIN` را نیز روی همان دامنه تنظیم کنید.
